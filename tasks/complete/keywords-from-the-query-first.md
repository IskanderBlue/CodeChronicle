# Take the keywords from the query, then let the LLM supplement

**Done on 14 August 2026, except the indirect weight, which measured as needing
no change. See "The result" and "The indirect weight" below.**

## The result

Same query, same date, same corpus. `9.8.8.3. Height of Guards` moves from
**rank 59 to rank 1**, and every one of the top eight results is now on topic.

| | Before | After |
|---|---|---|
| Rank of 9.8.8.3. | 59 of 419 | **1 of 924** |
| Its score | 0.9900 | 2.0220 |
| Top-8 results matching a typed word | 0 | 8 |

The new keyword list is `guard, height, stair, house` (the reader's own words),
then `guards, heights, stairs, houses` (the plural partners), then the model's
additions. The model still adds `residential`, and it no longer matters.

## Goal

Make the search score the words the reader typed. Today the LLM parser
*replaces* the query with keywords it infers, and an inferred word can outrank
every word the reader wrote.

## The measurement that started this

Query: `guard height for a stair in a house`, at 1 June 2008. This is the
article's own call to action, so it is the first search many readers run.

The parser returns `keywords: [guard, height, stair, residential]` and
`building_type: residential`. The word `residential` is not in the query.

The result, on the production path:

| Rank | Score | Provision | Direct terms | Indirect terms |
|---|---|---|---|---|
| 1 | 1.6200 | 9.10.9.12. Residential Suites, Live/Work Units | — | residential |
| 2 | 1.6180 | 9.33.2.1. Residential Heating Systems | — | residential |
| 3 | 1.6120 | 3.1.5.14. Storage Lockers in Residential Buildings | — | residential |
| **59** | **0.9900** | **9.8.8.3. Height of Guards** | **guard, height** | — |

The first eight results match `residential` only. They match no word the
reader typed. The answer is 59th of 80 results above the relevance floor.

Remove `residential` and 9.8.8.3. moves from rank 59 to rank 2.

## Why it happens

Three causes, all in `api/llm_parser.py`.

1. **The prompt asks for inference.** `SYSTEM_PROMPT` says "Keywords (what
   code topics are relevant?)". "Relevant" is not "present". A house is a
   residential building, so the model adds the word.
2. **The schema asks the same question twice.** `building_type` is a separate
   field with the enum `residential | commercial | industrial | assembly |
   institutional`. The model fills that field *and* mirrors the value into
   `keywords`.
3. **`building_type` is dead.** No code in `api/search/` or
   `core/views/search.py` reads it. Only the mirrored copy has an effect, and
   its effect is to score provisions that contain the word.

A fourth cause makes it worse. `score_versions` weights an indirect term at
**0.9** of a direct term. Nine-tenths is not a discount. A document that
matches one inferred word beats a document that matches two typed words.

## What to do

### 1. Drop `building_type`

Remove the field from the tool schema and from `SYSTEM_PROMPT`. Nothing reads
it. See `tasks/b-boost-parts-by-building-type.md` for the capability that
should replace it.

### 2. Extract the keywords locally, before the LLM runs

Use CCM's own tokenizer. The corpus `keyword_counts` come from it, so a query
tokenized the same way produces terms that can match.

Source: `src/chronicle_mapping/shared/keywords.py`,
`extract_keyword_counts(text)`. It does four things this needs:

- a letter-initial word regex,
- a hyphen split (`spruce-pine-fir` becomes three terms),
- a `STOPWORDS` filter and a "longer than 2 characters" rule,
- a provision-id and table-id pass, so a query that names `9.8.8.3.` gets the
  id as a term.

Vendor it, as `config/synonyms.py` was vendored.

**Two things this found in the doing.** First, `STOPWORDS` does not live in
CCM. `mcp_imports` reaches a *third* repository for it, through a `sys.path`
trampoline into `Canada_building_code_mcp`, and adds domain filler on top. The
combined 244-entry set is vendored as a literal, generated by running the real
import rather than typed by hand.

Second, **drop the id pass.** CCM adds dotted provision and table ids as terms
because a map file has no other channel for them. This product has one:
`api/llm_parser.py` extracts ids with its own regexes and hands them to the
engine as `section_references`, which score against a provision's number rather
than its text. Vendoring the id pass would build a second channel for something
already routed, and it is what drags in `PROVISION_ID_PATTERN`, `TABLE_PATTERN`,
`get_level_from_id` and, through them, BeautifulSoup.

That drop was checked, not assumed. CodeChronicle's reference channel catches
every id shape CCM's pass catches, and one it rejects:

| Query | Reference channel | Keywords |
|---|---|---|
| `guard height in 9.8.8.3.` | `9.8.8.3.` | `guard, height` |
| `Table A-1 climate` | `Table A-1` | `climate` |
| `see 9.8.8.3.(4) please` | `9.8.8.3.(4)` | `please` |
| `Division B 9.8` | `9.8` | — |

CCM's id pass rejects a dot-less `9.8`, because `get_level_from_id` reads it as
a decimal. The reference channel keeps it.

Then keep only the terms in `config/keywords.VALID_KEYWORDS` (7 094 entries).
That file is **fully overwritten** by `scripts/extract_keywords.py`, so the
derived set for fast membership must live in the new module, never beside it.

For the query above this gives `[guard, height, stair, house]`. Note `house`:
the code uses that word ("serving a house or an individual dwelling unit"),
and `residential` is the word the model invented in its place.

### 3. Let the LLM supplement, never replace

Send the extracted list to the model. Ask it to **add** terms only: plural and
singular forms, synonyms, and related code topics. Say that it must not remove
a term and must not return a list that omits one.

The engine already separates the two kinds, so the split maps onto machinery
that exists:

- the locally extracted terms are **direct**,
- everything the model adds is **indirect**.

Today that split is incidental — `score_versions` recovers it by comparing the
keywords against `raw_query`. After this change it is authoritative.

### 4. Decide the indirect weight

**Decided: leave it at 0.9. Do not add the promote-only rule.**

The proposal was to stop an indirect term from carrying a document on its own,
and let it only promote a document that already matches a typed word. The
evidence for it was that all eight top results matched nothing the reader
typed.

After steps 1 to 3, **no indirect-only document appears in the top 20**. The
ordering fault was never the weight. It was that the typed words were not in
the search at all, so `residential` had nothing to lose to.

The rule would also cost real recall. `plural_variants` puts both forms of a
word in the list, and only one of them can be the typed one. A provision whose
title says "Guard" where the reader typed "guards" matches on an indirect term
alone, and the rule would drop it. That is the failure the title field exists
to prevent.

Re-open this only with a query where an indirect-only document outranks a
direct match. Measure before changing the number.

## Rules

- **The tokenizer must be CCM's, not a new one.** The corpus index comes from
  that code. A second tokenizer is a second vocabulary, and terms that do not
  match are invisible.
- **A vendored copy needs a guard that points at the original.** A test of
  recorded expectations fails when the *copy* changes. It cannot fail when
  *CCM* changes, which is the direction that matters: CCM's tokenizer writes
  the `keyword_counts`, so a change there re-tokenizes the index at the next
  `load_edition` while the copy sits still. `TestNoDriftFromCCM` runs the real
  function in CCM's own venv, as a subprocess, and compares. It skips where
  the sibling clone is absent. Its first version was checked by breaking the
  copy: changing the minimum term length from 2 to 3 drops `fir` from
  `spruce-pine-fir`, and the test names that word.
- **The guard belongs in both repositories.** A test only fires for somebody
  who runs it, and a person changing the tokenizer is working in CCM, not
  here. So CCM carries the mirror — `tests/test_keyword_parity_codechronicle.py`
  runs this copy in this venv and compares — plus the obligation in the
  `shared/keywords.py` docstring and in its `CLAUDE.md`. That mirror was
  checked the same way, by changing CCM's length filter and confirming it goes
  red. Neither test runs in CI, because neither repository's CI clones the
  other; `CCM_SAMPLES` is the guard that does.
- **Say which difference is deliberate.** This copy omits CCM's id pass, so it
  is not the same function and must not claim to be.
  `test_the_id_pass_is_the_only_difference` pins both sides of the one gap.
- **The typed words can never be dropped.** The union in `_merge_keywords` puts
  them back whatever the model returns, so this is a property of the code and
  not a request the model may or may not honour.
- **Both forms of a word go in.** CCM's tokenizer does no stemming, so `stair`
  does not match `stairs`. Both are in `VALID_KEYWORDS`. `plural_variants`
  adds the partner locally, rather than leaving it to the component this work
  exists to stop depending on. The partner is indirect: the reader did not
  type it, and 0.9 is the discount a variant should carry.
- **A query with no valid keyword still reaches the model.** "How do I do this"
  holds no word the corpus uses. The model is what saves that query, so local
  extraction is a floor, not a gate.
- **A stopword stays a stopword.** `building`, `minimum` and `code` look like
  the most relevant words a reader could type. The same filter ran over every
  provision, so no `keyword_counts` dict holds them, and keeping one would
  produce a term that matches nothing.

## Done

- `building_type` is gone from the schema, the prompt and the parser. It was
  named in no other code file.
- `config/query_keywords.py` extracts the keywords, and the LLM receives them
  as "Words in the query".
- The prompt asks the model to add terms and never to remove one, and names
  the `house` / `residential` failure so it does not repeat it.
- `guard height for a stair in a house` at 1 June 2008 puts 9.8.8.3. **first**.
- `api/tests/test_query_keywords.py` (17 tests) and
  `TestTheQueryIsReadBeforeTheModel` in `api/tests/test_llm_parser.py`
  (6 tests) pin the tokenizer, the union and the direct/indirect split. No
  test asserts the wording of a prompt.

## What this did not do

The direct/indirect split is now **stated** by the parser rather than derived
by the engine, and the derivation stays as the fallback for a caller that
sends none. That is worth keeping in mind, because the derivation was subtly
wrong: its regex does not split hyphens, so a typed `spruce-pine-fir` extracts
as three terms, no one of which appears verbatim in the query, and all three
were filed as the model's guesses.

## To undo

Revert the parser change. The prompt is versioned by hash in `QueryPrompt`, so
a rollback is visible in that table. Cached parses under the old prompt stay
valid; they are keyed by the prompt hash.
