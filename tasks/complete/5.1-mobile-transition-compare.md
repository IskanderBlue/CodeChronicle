# 5.1 — Mobile Transition Compare

## Status: complete (browser-verified 2026-07-23)

## What

Make transition compare cards work on small screens.

## Why

The desktop side-by-side compare panes do not fit on a phone.

## What shipped (and why it is not the original plan)

The original plan here was a **mobile tab switcher** (Old / New tabs, one pane
visible at a time). That was built on 2026-03-08 in `5daff64` as
`data-transition-mobile-tabs` in `search_results_partial.html`.

It was then **deliberately replaced** on 2026-04-15 by `1601123`
("feat: implement provenance display, regulation browsing, edition chain"),
whose commit message lists the change explicitly:

> Transition compare:
> - Stacked accordion: primary version open, previous collapsed
> - Versions labeled by regulation (O. Reg. X version), not "Current"

So the tabs were retired on purpose, not lost. This doc described the
superseded design for three months; it is corrected here rather than treated
as a regression.

**Current design.** The layout forks on the `metadata_in_rail` flag, not on a
CSS breakpoint alone — both branches render server-side and CSS picks between
them at `lg` (1024px):

- `_result_expanded.html:107` (`metadata_in_rail=True`) — desktop master-detail
  side-by-side focus-compare; expanding "previous" collapses the results list so
  the two panes share the width.
- `_result_expanded.html:145` (flag unset, wrapped in `lg:hidden`) — mobile
  stacked accordion: the in-force version renders first, the previous version
  sits behind a collapsed `showPrevious` toggle beneath it.

**Why stacking is acceptable here.** Comparison on mobile does not depend on
seeing both versions at once. Each pane renders `diff_html` by default
(`_result_document_block.html:94`, `x-data="{ expanded: false, showDiff: true }"`)
with a "Show original" / "Show diff" toggle. The diff is inverted: `_render_side`
(`api/formatters.py:170`) wraps only the *unchanged* words in
`.diff-old-unchanged` / `.diff-new-unchanged`, which `base.html:114` dims to
`opacity: 0.7`. Changed words are left unwrapped and read at full strength, so
each pane self-describes what changed.

## Completion Conditions

- [x] Transition compare cards are usable on narrow screens.
- [x] Banner content remains visible and readable.
- [~] Old/new switching works **without stacking full versions vertically** —
      not met literally; expanding "previous" grows the page ~589px and pushes
      the in-force pane below it. Accepted, because the per-pane inline diff
      carries the comparison (see above), which is what this condition was
      protecting.

branch and utilities apply; only very narrow wrapping is untested.

## Fix made during verification

Both panes rendered the identical label `22/98 version`. The label was
`version.clause.regulation.reg_id`, derived independently in each pane — and a
single clause can produce *both* members of a pair (a cascading renumber amends
a run of articles in one directive), so the regulation alone stopped telling the
panes apart. A pane can't detect this on its own; it can't see the other pane.

Moved the derivation into `merge_transition_compare_results`, which already
holds both members. It stamps `pane_label` on each; when the two would collide,
each leads with its own provision id:

- `9.23.9.6. · 22/98 version (previous)` / `9.23.9.7. · 22/98 version`
- rail: `9.23.9.6. · 22/98 · PREVIOUS`

All five inline derivations (four panes in `_result_expanded.html`, the heading
in `_result_rail.html`) now read `{{ version.pane_label }}`. Covered by three
formatter tests, including the base-enactment case where neither version has a
clause and both fall back to the same edition display name.

## Reproducing a card (non-obvious)

`merge_transition_compare_results` only emits a card when **both** pair members
independently rank into the same result set
(`if not old_result or not new_result: continue`). `get_applicable_codes` returns
exactly one edition per code per date (`.first()`), and OBC editions abut with no
overlap — OBC 2006 ends 2014-01-01, OBC 2012 begins 2014-01-01. So no search date
returns two OBC editions, and **all 3,128 cross-edition mappings are unreachable
through normal search**. Only the 5 intra-edition OBC 1997 renumbers can produce
a card, and OBC 1997 is dev-only (`verified=False`, not on prod) — so this card
type cannot currently be reproduced on production at all.

## Open Issues / follow-ups

- `core/views/search.py:82` claims the maintenance-inspection chip yields a
  `1.10.2.4.` transition_compare card at 2014-07-01. It does not — swept nine
  dates 2013-06-01 → 2015-01-01, zero transition cards. The comment (and the
  chip's premise) are stale for the current data. Needs its own task.
- `_diff_html_content`'s docstring claims asymmetric styling ("old lowlighted,
  new highlighted"), but `_render_side` wraps unchanged words on both sides and
  `base.html:114` dims both identically. Behaviour is symmetric; docstring is
  wrong. Cosmetic.
- Keyword-match highlighting (`mark.match-highlight`) and diff dimming are two
  independent emphasis systems layered on the same sentence; they compete
  visually. Worth a design pass if compare gets revisited.

## Notes

- Diff mode turned out **not** to be optional — it is what makes the stacked
  accordion viable on mobile, and is the reason this task can close without tabs.
- Dev gotcha hit during verification: template edits are not hot-reloaded despite
  `DEBUG=True` (Django's default loaders cache in-process). `runserver --noreload`
  serves stale templates until restarted.
