{% load humanize %} {% comment %} What a provision contains, when the provision is too big to show as text. `contents`: rows from core.views.regulation._contents_rows — a _permalink_nav_item item ({provision_id, title, versions:[…]}) plus `child_count` and `child_noun`. Shared by the reading page, the exhibit and the search overlay. An exhibit must not show something the page does not, and a reader who meets the contents of Part 9 in the overlay and again on its own page must meet one list. All three mount this file over core.subtrees.contents_view; none builds its own. So the copy names no surface — "on one page" was wrong in a panel beside the search results, which is not a page. The register is the navigation's — mono ids, italic titles, `ui-cite` links — because these rows point at other provisions, which is exactly what a nav row does. The layout is not the navigation's: that partial is built for the narrow `--ws-nav` rail and truncates on one line, and this block sits in the centre column where a title has room to finish. The right-hand measure carries two facts, and the second is the argument for this page existing at all: how much is inside, and whether the text changed while it stood. A row that names two versions is an invitation to compare — the one question no other website answers about this corpus. A row with a single overlapping version links as a whole. With several there is no single target, so the id and title become text and each version gets its own dated link, the same rule `_permalink_nav_item.html` follows. {% endcomment %}
